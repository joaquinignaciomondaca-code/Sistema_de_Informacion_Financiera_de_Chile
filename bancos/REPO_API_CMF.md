# Diagnóstico de REPO bancario desde ZIP públicos CMF

**Estado: exploración, sin publicación.** Los scripts facilitados por el usuario muestran que `repo_banco.xlsx` se creó a partir de ZIP de balances mensuales de la CMF, con tipo de cambio opcional de la API CMF o BCCh. Sólo recibimos los programas principales, no los módulos `src/downloader.py`, `src/parser.py`, `src/exporter.py`, `src/bcch_client.py` ni el Excel: aún no se puede certificar/reproducir exactamente la transformación original. **La tabla REPO publicada queda intacta y sigue pendiente de auditoría.**

El workflow diario `bancos_repo.yml` descarga ZIP públicos de [Balance y Estado de Resultados en texto](https://www.cmfchile.cl/portal/estadisticas/626/w4-propertyvalue-32901.html), sin `USER_CMF`, `PASSWORD_CMF` ni API key. Primero consulta el índice web (para enlaces nuevos), toma el catálogo del repositorio sólo para periodos históricos y se detiene ante discrepancias de versiones no resueltas. El cotejo `bancos/scripts/audit_repos_zip_cmf.py` inspecciona B1/B2 de **todos los bancos del ZIP** por mes y produce un JSON con cuentas crudas candidatas, SHA-256 del ZIP y posibles escalas/columnas que coinciden con la tabla antigua. Una coincidencia no certifica cuenta, unidad ni origen: es evidencia para inspección humana. Los códigos `1160000/2160000` antes de 2022 y `141000000/243000000` desde 2022 aparecen como pistas en el script V2 del usuario, **no como un mapeo validado**. Se debe contrastar el parser real, las unidades, subtotales y rupturas de plan antes de transformar o sumar cuentas. No se usa WinRAR: Python verifica y lee los ZIP en memoria. La comparación por cuenta genera candidatos de divisor (1.000 o 1.000.000) **sin seleccionar automáticamente ninguno**. No se inventan RUT ni tipos de cambio y no se produce Parquet ni Excel.

**Ejecución:** Actions → «Cotejo ZIP CMF — REPO bancario (sin publicación)» → Run workflow (mes opcional, p. ej. `2021-12` o `2026-04` para calibración). Un push a la rama de sesión ejecuta automáticamente una muestra `2021-12` (sin checkpoint); la corrida diaria o manual sin mes consulta sólo desde el último mes conservado en `docs/outputs/bancos/bancos_repos_saldos_series.json` o el checkpoint de diagnóstico posterior, hasta el último mes completo y máximo 12 meses por corrida. Se reconsulta el último mes guardado para detectar revisiones. El artefacto `cotejo-repo-zip-cmf` contiene el JSON de evidencia. El checkpoint usa la caché de Actions y solo se guarda tras procesar todo el lote; la caché puede expirar y no sustituye un histórico versionado validado. Si falla red, ZIP, período, archivo o estructura, el job falla sin actualizar datos públicos. Si el índice CMF cambia o no lista meses esperados, investigar antes de asumir que no hubo publicación.

**Seguridad:** los ZIP públicos no usan credenciales. `USER_CMF`/`PASSWORD_CMF` no se envían como `apikey`. La API bancaria autenticada es otra vía; requiere una clave separada `CMF_API_KEY` y no se necesita para este diagnóstico. El workflow anterior que adivinaba cuentas/unidades, asignaba RUT cuestionados y reemplazaba el REPO fue retirado para evitar publicar cifras erróneas.

**Resultado de la prueba en Actions (27-09-2026):** la [corrida `36295641476`](https://github.com/joaquinignaciomondaca-code/monitor-financiero-chile/actions/runs/36295641476) llegó a descargar el índice CMF (título correcto, 857.021 caracteres, 782 enlaces) y **sí encontró 296 enlaces ZIP válidos**. La falla fue de nuestro parser: `discover()` exigía que el *texto* de cada ancla contuviera «`<mes> <año>`», pero el índice real rotula el mes fuera del texto del enlace (p. ej. en el encabezado «Balance y Estado de Situación Bancos Julio 2026» que acompaña a la descarga, o en un atributo `title`/`alt`). **No era un bloqueo de red de la CMF ni ausencia de ZIP.** Los ZIP reales aún **no se cotejaron**: las pruebas locales usan ZIP sintéticos, y la conexión CMF desde este entorno local termina en error TLS.

**Corrección aplicada (parser de períodos).** `ZipLinks` ahora conserva un flujo documental ordenado (anclas y textos) y `discover()` resuelve el período con señales en este orden: texto del ancla → atributos `title`/`aria-label`/`aria-labelledby` del ancla o `alt`/`title` de su ícono → encabezado que sigue al enlace hasta el próximo enlace ZIP. Nunca se deduce el mes desde el id del artículo, la fecha de publicación ni el nombre del archivo del `href`. Como red de seguridad, el cotejo compara el período de cada archivo interno (`b1AAAAMMBBB.txt`) con el mes solicitado y **falla en vez de asignar mal un mes**. Si el índice vuelve a cambiar, el mensaje de error incluye una muestra limpia (sin etiquetas HTML) de las señales de los primeros enlaces ZIP para corregir el parser sin adivinar. El código también reintenta errores de red/servidor y conserva evidencia parcial si falla un mes posterior, siempre sin avanzar el checkpoint. **No se interpreta una falla de red ni de HTML como ausencia de datos.** Los artefactos de falla sólo guardan el mensaje de diagnóstico; no contienen cifras bancarias cotejadas.

**Para avanzar a extracción diaria verificable:** aportar o integrar `src/parser.py`, `src/downloader.py` y `src/exporter.py` del proyecto local (sin credenciales ni archivos pesados), comparar por código y mes con reportes CMF y la tabla histórica; definir reglas de cuentas/escala por fecha, total vs detalle, ceros vs ausencias, revisiones y fechas. Crear entonces un extractor incremental desde los ZIP, auditado antes de cualquier publicación. No borrar el REPO actual ni quitar la advertencia antes de ese cotejo.

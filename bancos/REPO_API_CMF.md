# Diagnóstico de REPO bancario desde ZIP públicos CMF

**Estado: exploración, sin publicación.** Los scripts facilitados por el usuario muestran que `repo_banco.xlsx` se creó a partir de ZIP de balances mensuales de la CMF, con tipo de cambio opcional de la API CMF o BCCh. Sólo recibimos los programas principales, no los módulos `src/downloader.py`, `src/parser.py`, `src/exporter.py`, `src/bcch_client.py` ni el Excel: aún no se puede certificar/reproducir exactamente la transformación original. **La tabla REPO publicada queda intacta y sigue pendiente de auditoría.**

El workflow diario `bancos_repo.yml` descarga ZIP públicos de [Balance y Estado de Resultados en texto](https://www.cmfchile.cl/portal/estadisticas/626/w4-propertyvalue-32901.html), sin `USER_CMF`, `PASSWORD_CMF` ni API key. Primero consulta el índice web (para enlaces nuevos), toma el catálogo del repositorio sólo para periodos históricos y se detiene ante discrepancias de versiones no resueltas. Examina B1/B2 de **un banco de prueba** (`001`) por mes, expone líneas crudas de los prefijos 116/216/141/243 y hashes SHA-256 del ZIP para comparar con los saldos anteriores. Los códigos `1160000/2160000` antes de 2022 y `141000000/243000000` desde 2022 aparecen como pistas en el script V2 del usuario, **no como un mapeo validado**. Se debe contrastar el parser real, las unidades, subtotales y rupturas de plan antes de transformar o sumar cuentas. No se inventan RUT ni tipos de cambio y no se produce Parquet ni Excel.

**Ejecución:** Actions → «Diagnóstico ZIP CMF — REPO bancario (sin publicación)» → Run workflow (mes opcional, p. ej. `2021-12` o `2026-04` para calibración). Sin mes, consulta sólo desde el último mes conservado en `docs/outputs/bancos/bancos_repos_saldos_series.json` o el checkpoint de diagnóstico posterior, hasta el último mes completo y máximo 12 meses por corrida. Se reconsulta el último mes guardado para detectar revisiones. El artefacto `diagnostico-repo-zip-cmf` contiene el JSON de evidencia. El checkpoint usa la caché de Actions y solo se guarda tras procesar todo el lote; la caché puede expirar y no sustituye un histórico versionado validado. Si falla red, ZIP, período, archivo o estructura, el job falla sin actualizar datos públicos. Si el índice CMF cambia o no lista meses esperados, investigar antes de asumir que no hubo publicación.

**Seguridad:** los ZIP públicos no usan credenciales. `USER_CMF`/`PASSWORD_CMF` no se envían como `apikey`. La API bancaria autenticada es otra vía; requiere una clave separada `CMF_API_KEY` y no se necesita para este diagnóstico. El workflow anterior que adivinaba cuentas/unidades, asignaba RUT cuestionados y reemplazaba el REPO fue retirado para evitar publicar cifras erróneas.

**Para avanzar a extracción diaria verificable:** aportar o integrar `src/parser.py`, `src/downloader.py` y `src/exporter.py` del proyecto local (sin credenciales ni archivos pesados), comparar por código y mes con reportes CMF y la tabla histórica; definir reglas de cuentas/escala por fecha, total vs detalle, ceros vs ausencias, revisiones y fechas. Crear entonces un extractor incremental desde los ZIP, auditado antes de cualquier publicación. No borrar el REPO actual ni quitar la advertencia antes de ese cotejo.
